# 06: Audit trail: triggers, actor resolution, and the audit tab

**What to build:** Every change to a tracked record becomes an audit event naming the actor, the time, and the values before and after, whether the change came from a nurse in the UI or from the simulator's service-role path. The resident page gains an audit trail tab that reads like a story of who did what, with a before-and-after view for each event.

**Blocked by:** 05 (Recording care: create and edit flows)

**Status:** resolved

- [x] An audit events table and database triggers cover every tracked table from the spec, capturing operation, row identity, and before-and-after values
- [x] The actor is resolved from the authenticated user when present, otherwise from a session setting that service-role callers must provide; a write with neither is rejected
- [x] Audit events are readable within the same scope as the record they describe, via policies
- [x] The resident page has an audit trail tab listing events newest first with actor, time, record type, and a readable summary, and expands to a field-by-field before-and-after view
- [x] Trigger tests prove that a change through a user session and a change through the service-role path with an actor setting both produce a correct audit event, and that the archive flows from ticket 05 are captured as changes, not deletes
- [x] The audit trail tab is included in the resident page's "not found" behavior for out-of-scope residents

## Comments

**2026-09-10, agent.** Implemented and verified against the hosted project.

- **Database** (`supabase/migrations/20260910180000_audit_trail.sql`, applied with `pnpm db:push`): an `audit_events` table (actor, time, resident, table and row, operation, the whole row before and after as JSON, and the changed columns on an update) with an `after insert or update or delete` row trigger, `record_audit_event()`, on residents and the thirteen clinical tables. An update that changes nothing but `updated_at` writes no event. The residents trigger covers inserts and updates only: a resident row is never removed, and the foreign key from the trail stops a hard delete of any resident with one. `current_actor_id()` resolves the actor: a signed-in user is themself, whatever else the request says; a service-role caller names the staff member on each request through the `x-caredesk-actor` header (PostgREST exposes request headers as a setting; supabase-js sends it from `global.headers`) or `app.actor_id` in a direct SQL session; a write with neither, or naming someone who is not staff, is rejected with a message that says so (hint `no_actor`). Events are readable in the resident's scope (the same policy expression as every clinical table) and append-only: `insert`, `update`, and `delete` are revoked from signed-in staff and the trigger function is `security definer`. The table is in the Realtime publication for ticket 07. `reset_demo_data()` now truncates the trail too. A second migration (`20260910183000_operator_wide_staff_visible.sql`) lets every signed-in staff member see operator-wide staff (those with no facility, the admin), so a change the admin made is attributed by name on a nurse's screen instead of "a staff member outside your scope". Documented in `docs/database.md`, "Audit trail".
- **The seed is not audited.** The spec says the seeder and the simulator "both set an explicit actor". The simulator will; the seeder instead sends `x-caredesk-audit: skip`, which the trigger honors only for a request with no user session, because the seed is the starting state, not a change, and 57,000 "created by the admin at reseed time" events would drown the story on every resident's page. A nurse sending the same header is audited all the same (tested). If you would rather the seed produce events, it is one header change in `scripts/seed/reset.ts`.
- **Server** (`src/lib/audit/`): `events.ts` reads a resident's events through the caller's session with the actor joined and the true total, and resolves the names behind foreign keys (rooms, units, staff, medication orders) through their own policies. `describe.ts` is pure: it turns an event into a sentence ("recorded vitals", "gave Simvastatin", "discontinued the Metformin order", "moved the resident to Room 214, Unit B", "changed the resident's diet from Regular to Diabetic", "removed the Penicillin V allergy", "made Jane Doe the primary contact", "discharged the resident") and a field-by-field before-and-after list; removals read as "removed", a service-role hard delete as "deleted". `columns.ts` holds each table's field labels and formats (enumerations by display label, dates and times in Eastern, foreign keys by name, bookkeeping columns hidden). `groupByDay` and `dayHeading` moved into `src/lib/time.ts` and the clinical timeline uses them too.
- **UI (ADR 0004)**: an "Audit trail" tab at the end of the record tabs (`?tab=audit`, count badge with the true total), newest first, grouped by day, each event a `<details>` row with an icon for added, changed, or removed, the actor's name in bold, the sentence, the time and record type, and, open, a Field / Before / After table (Field / Value for additions and removals) plus an "Open medications" link to the record's tab. Shows the 25 newest, folds the rest behind "Show N older changes", and reads at most 200 with a note when there are more. The tab is on the resident page, so an out-of-scope resident is the same 404 with `?tab=audit`.
- **Tests**: 120 pass across 16 files. `describe.test.ts` (14) covers the sentences and the field lists. `triggers.integration.test.ts` (8) runs against the hosted project: a nurse's write is attributed to her with the new values and reads as "recorded vitals" with her name; an update records only the changed column before and after and a no-op records nothing; the simulator's path with the actor header is attributed to the simulated nurse and reads the same; the service role naming nobody, a stranger, or garbage is rejected and nothing lands; the seeder's skip flag silences the trigger for the service role only; add-then-archive is insert then update of `archived_at`, cancel is an update of `status`, and only a service-role hard delete is a delete; the admin's note for a Harbor resident is invisible to the Meadows nurse and visible to the Harbor nurse and the admin; signed-in staff cannot insert, update, or delete events. The ticket 04 and 05 integration tests now put the seed back with the skip flag and delete the events their writes produced (their cleanup used to be a bare service-role delete, which the actor rule now rejects).
- **Verified live** on the dev server with headless Chrome as the nurse at 1280 and 400 px: six events on Jacques Olson (Room 205, Unit B, Meadows) from both paths rendered as described, no horizontal overflow, no console errors. Everything was put back except one reverted diet change, so his audit trail shows two events for review. `pnpm check` and `pnpm build` are green.
