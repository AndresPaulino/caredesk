# 05: Recording care: create and edit flows

**What to build:** A nurse can do the work of a shift from the resident page: edit the resident's details, record vitals, add or discontinue a medication order, mark a medication as given with one click, write a progress note, report an incident, schedule or cancel an appointment, add or edit a family contact, and add an allergy. Removals archive the record instead of destroying it. Every form validates and explains mistakes.

**UI approach (ADR 0004):** forms use `@shadcn/form` with the zod schemas the server validates against; create and edit flows open in `@shadcn/sheet` (or `@shadcn/dialog` for one-field actions such as marking a medication given) from the record tabs, so the resident page stays in place.

**Blocked by:** 04 (Resident detail with clinical timeline and record tabs)

**Status:** resolved

- [x] Edit flows exist for resident details (demographics, room, status, code status, diet, mobility) with room changes keeping room occupancy consistent
- [x] Create flows exist for vitals, medication orders, progress notes, incidents, appointments, family contacts, and allergies; discontinue exists for medication orders; cancel exists for appointments
- [x] A one-click "mark given" action on an active medication order records an administration attributed to the signed-in nurse with the current time
- [x] Removing an appointment, contact, or allergy archives it; archived records disappear from default views and remain in the database
- [x] Assessments, lab results, conditions, and care plans are read-only in the UI
- [x] All input is validated with zod on the server; errors are shown next to the field that caused them
- [x] Write policies allow a nurse to write only within scope and an admin everywhere; a test attempts an out-of-scope write as the nurse and asserts rejection
- [x] The resident page and timeline reflect each change immediately after submit

## Comments

**2026-09-10, agent.** Implemented and verified against the hosted project.

- **Database** (`supabase/migrations/20260910150000_recording_care.sql`, applied with `pnpm db:push`): the write policies from tickets 02 and 03 already let a nurse write within scope and an admin everywhere, so the migration adds the rules the flows need from the database itself. A `security definer` trigger, `enforce_room_capacity`, locks the room and rejects placing a current resident where every bed is taken (check violation, hint `room_full`); a constraint, `residents_former_holds_no_room`, frees the bed when a stay ends; `residents (room_id)` is indexed. The insert policies on vitals, administrations, progress notes, incidents, and appointments now also require the "by" column to be `current_staff_id()`, so a nurse records care in their own name. Medication orders stay as they were: `prescribed_by` is a physician and the nurse enters the order on their behalf. Documented in `docs/database.md`.
- **Server** (`src/lib/care/`): `schemas.ts` holds one zod schema per form, validated in the browser for instant feedback and again in the server action before writing, with messages written for the person filling in the form; times typed into a form are Eastern wall-clock times and become instants there. `record.ts` is the seam: one function per write over the caller's own Supabase client (ADR 0003), returning "forbidden" on a policy rejection, "not found" when an update matches no visible row, and a field-specific message for the room-capacity trigger, an unknown formulary entry, or a prescriber who is not a physician. Archiving stamps `archived_at`; nothing is deleted. `actions.ts` holds the server actions (authenticate, parse, write, `refresh()` so the page shows the change in the same round trip). `options.ts` reads physicians and the units and rooms with occupancy through the caller's session; `vocabulary.ts` derives the formulary and the allergen list from the clinical vocabulary the seed uses, so recorded orders and allergies are indistinguishable from seeded ones and the conflict rule keeps working.
- **UI (ADR 0004)** in `src/components/residents/care/`: `useCareForm` wraps `useActionState` with the shared schema; `CareForm` inside `@shadcn/sheet` for every create and edit flow (`@shadcn/field` with native selects, `@shadcn/textarea`, `@shadcn/checkbox`); `ConfirmActionDialog` on `@shadcn/dialog` for discontinue, cancel, mark refused or held, and remove; `RowActionsMenu` on the dropdown menu; `@shadcn/sonner` toasts confirm each change. "Edit details" sits in the page header (units the caller covers, rooms with free-bed counts, full rooms disabled, ending a stay frees the room). Each writable tab gained an add button in its heading and row actions: medications (one-click "Mark given", plus refused, held, and discontinue; the order form searches the formulary through a native datalist, preselects the usual frequency, and warns as you type when the medication names a documented allergen), vitals, allergies (remove), incidents, progress notes, appointments (cancel keeps the record as cancelled, remove archives), family contacts (edit, remove; one primary contact per resident). A former resident's record takes no new care: create actions are hidden except details, contacts, and allergies. Conditions, lab results, care plans, and assessments have no forms and say so in their descriptions. `RecordPanel` gained an `actions` slot. The dialog component was written by hand from the registry because `pnpm shadcn add` stops at an "overwrite button.tsx?" prompt for anything that depends on button.
