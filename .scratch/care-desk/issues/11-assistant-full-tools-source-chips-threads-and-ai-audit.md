# 11: Assistant: full tool set, source chips, saved threads, and AI audit

**What to build:** The assistant can answer questions about every record type and about the audit trail itself: "who updated his medications yesterday", "what changed in her medications since she came back", "which residents on Unit B have an allergy conflict". Every answer carries source chips linking to the records used. Threads are saved and can be resumed. Every question and every tool call is written to the audit trail as an assistant access event.

**Blocked by:** 06 (Audit trail: triggers, actor resolution, and the audit tab), 10 (Assistant: drawer, streaming, and the core tools)

**Status:** ready-for-human

- [x] Additional tools, all scoped through the caller's session: get lab results, get incidents, get progress notes, get appointments, get family contacts, get a resident's audit trail, get recent activity for a unit or facility, and check allergy-to-medication conflicts for a resident or a unit
- [x] Source chips are built from the records the tools returned and link to the resident page and the relevant tab
- [x] Threads and messages persist per staff member with policies allowing only the owner to read them; the drawer lists past threads and resumes one
- [x] Each question and each tool call is recorded as an audit event attributed to the asking staff member, and those events appear in the activity feed and in the resident's audit trail tab when they concern a resident
- [x] The assistant remains read-only; no tool has side effects beyond the audit record
- [x] Integration tests cover every new tool as the nurse and the admin, including the allergy conflict check finding the hero resident with the conflict and the audit trail tool returning the simulator's or a user's recent change
- [x] A manual check confirms the three questions above produce correct, sourced answers for the hero residents

## Comments

**2026-09-15, agent.** Built and checked on the hosted project; both migrations are applied there.

- Tools: `src/lib/assistant/tools/` is now a directory (`core.ts` the six from ticket 10, `records.ts` lab results, incidents, progress notes, appointments, family contacts, `audit.ts` a resident's audit trail and recent activity for a unit or facility, `conflicts.ts` the allergy conflict check for a resident or a scope, `shared.ts` the context, `resolveScope` for "Unit B" / "Harbor" within the caller's scope, and date inputs that take a calendar date or an instant). Every resident-scoped result carries `source`; the two multi-resident tools carry `sources`. `tool-definitions.ts` wraps all fourteen; `get_recent_activity` and `check_allergy_conflicts` take `unit` and `facility`, and a unit is labeled with its facility because every facility has a Unit B. The audit tools leave assistant access events out unless asked, so "what changed" is about the records.
- Source chips: each `tool` done event carries the sources it read; the drawer merges them per resident and tab under the answer as chips linking to the resident page and tab (`residentHref`), and closes when one is followed.
- Threads: migration `20260915100100_assistant.sql` adds `assistant_threads` (owner `staff_id`, titled by the first question) and `assistant_messages` (position, role, content, the current resident, and for an answer `steps`, `sources`, `ended`, `error`), owner-only policies (the admin cannot read a transcript; the audit trail is the accountable record). The route now takes `{ threadId, question, residentId }`, saves the question before the model runs and the answer after (`src/lib/assistant/threads.ts`), and the drawer lists past threads and resumes one through server actions (`src/lib/assistant/actions.ts`). A resumed thread shows its status lines, chips, and "About Harold Doe" captions.
- Assistant access events: `audit_operation` gains `access` (its own migration, `20260915100000`, because Postgres will not use a new enum value in the transaction that adds it); `audit_events.resident_id` is nullable for `access` alone; `record_assistant_access(message_id, resident, details)` (security definer, checks caller, thread ownership, and resident scope) is the only writer. The route records the question before the model runs and each tool call before its result goes back to the model (a lookup that cannot be recorded fails). Events about a resident read in the resident's scope; one about nobody (a search, a unit-wide check) reads for the asker and admins. `describeAuditEvent` tells them as "asked the assistant about Harold Doe: “…”" and "read Harold Doe's audit trail for medications through the assistant" (story kind `accessed`, Sparkles icon) in the feed and the audit tab. Details shape and sentences: `src/lib/assistant/access.ts`.
